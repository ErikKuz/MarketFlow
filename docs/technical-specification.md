# MarketFlow MVP: техническое задание

## Цель

Реализовать и проверить минимальный многопродавцовый путь:

```text
регистрация → каталог → корзина → заказ → оплата → обработка → доставка → получение
```

## Архитектура

```text
HTTP → Spring Security → MVC/REST Controller
     → Service (@Transactional)
     → Spring Data JPA / Hibernate
     → PostgreSQL
```

Flyway управляет схемой, OpenAPI описывает REST, Thymeleaf формирует HTML.

## Требования

### Пользователь и безопасность

- регистрация `BUYER` или `SELLER`;
- вход через серверную HTTP-сессию;
- роли `BUYER` и `SELLER`;
- проверки принадлежности ресурса;
- CSRF для изменяющих запросов;
- запрет входа заблокированным и удалённым аккаунтам.

### Каталог и корзина

- продавец управляет только своими товарами;
- покупатель видит активные товары с остатком;
- позиции корзины имеют количество и признак выбора;
- выбранные строки блокируются при оформлении.

### Заказ

- сохраняются общий заказ и снимки товаров;
- создаётся одна часть на каждого продавца;
- стоимость вычисляется через `BigDecimal`;
- после создания выбранные позиции удаляются из корзины;
- создание выполняется одной транзакцией;
- неоплаченный заказ можно отменить.

### Оплата

- карта принадлежит покупателю и активна;
- хватает условного баланса;
- остаток каждого товара уменьшается атомарно;
- карта, остаток, транзакция и статусы меняются вместе;
- одна попытка создаёт одну запись `PAYMENT`;
- успешный ключ идемпотентности безопасно повторяется;
- недостаток товара откатывает всю операцию;
- недостаток денег сохраняет `FAILED` без списания.

### Доставка нескольких продавцов

```text
SellerOrder: NEW → PROCESSING → SELLERSENDPRODUCT → USERGETPRODUCT
Order: CREATED → CONFIRMED → SELLERSSTARTWORK → SELLERSENDWORKANDSEND → COMPLETED
```

Продавец работает только со своей частью. Покупатель подтверждает её получение. Общий `COMPLETED` допустим только после всех `USERGETPRODUCT`.

## Не входит в MVP

Заявки продавцов, модерация, кошельки продавцов, комиссия, вывод средств, возвраты после оплаты, аналитика, бизнес-аудит и дедлайн оплаты.

## Проверка готовности

- проект и тесты компилируются;
- unit-, repository-, MVC- и security-тесты проходят;
- PostgreSQL-тесты проверяют свежую миграцию и обновление V11 → V12;
- проверены параллельная оплата, последний остаток и заказ с двумя продавцами;
- документация и OpenAPI соответствуют коду.

После этого добавляется RabbitMQ для событий, не влияющих на атомарность основной транзакции.
